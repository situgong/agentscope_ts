# AgentScope Workspaces & MCP Gateway Architecture Guide

This document records our technical breakdown of **AgentScope 2.0 Workspaces**, the seven execution environment backends, the **MCP Gateway** architecture, and how both `stdio` and `HTTP` Model Context Protocol (MCP) servers are installed, isolated, and executed inside sandboxes.

---

## 1. Overview of the Seven Workspace Backends

In AgentScope, a **Workspace** is the agent's execution environment. It supplies built-in tools (`Bash`, `Read`, `Write`, `Glob`, `Grep`), manages markdown skills (`skills/`), handles context offloading, and owns the lifecycle of MCP servers. Because all seven implementations derive from `WorkspaceBase` and expose the same interface, agent code runs against any backend without changes.

### 1.1 Host & Lightweight Local Environments
* **Local (`LocalWorkspace`)**
  * **What it is:** Runs directly on your host machine's operating system without containerization or isolation.
  * **Persistence:** Saves files directly to a specified `workdir` directory on your local filesystem.
  * **Best for:** Quick local prototyping and trusted tasks where sandboxing overhead isn't needed.
* **Bubblewrap (`BubblewrapWorkspace`)**
  * **What it is:** Uses Linux Bubblewrap (`bwrap`), an unprivileged sandboxing tool that isolates processes using Linux namespaces (restricting filesystem and process views) without a container daemon. Note that `BubblewrapWorkspace` shares the host network namespace (`share_net=True`) so the host can reach the gateway over loopback.
  * **Persistence:** Mounts a host directory (`host_workdir`) read-write at `/workspace` inside the sandbox, or uses an ephemeral temporary directory if omitted.
  * **Best for:** Fast, lightweight OS-level process and filesystem isolation on Linux machines.

### 1.2 Container & Cluster Environments
* **Docker (`DockerWorkspace`)**
  * **What it is:** Runs the agent's tools and MCP servers inside an isolated Docker container.
  * **Persistence:** Bind-mounts a host `workdir` to `/workspace` inside the container (or runs as an ephemeral container if no host path is provided).
  * **Best for:** Standardized local development or single-server deployments where reproducible dependencies and strong container isolation are required.
* **Kubernetes (`K8sWorkspace`)**
  * **What it is:** Provisions a dedicated Kubernetes Pod as the agent's execution sandbox.
  * **Persistence:** Uses a PersistentVolumeClaim (PVC) mounted into the Pod, reattaching automatically via a workspace-ID-derived name across restarts.
  * **Best for:** Enterprise, cloud-native, or large-scale multi-agent deployments running on Kubernetes clusters.

### 1.3 Cloud & Purpose-Built AI Sandboxes
* **E2B (`E2BWorkspace`)**
  * **What it is:** Connects to E2B, a managed cloud platform that spins up secure, Firecracker microVM-based sandboxes built specifically for AI code execution and tool use.
  * **Persistence:** Stored directly on the remote sandbox filesystem and reattached via sandbox metadata.
  * **Best for:** Serverless AI applications needing instant, secure, zero-maintenance cloud sandboxes for untrusted code execution.
* **Daytona (`DaytonaWorkspace`)**
  * **What it is:** Targets a Daytona deployment (an open-source/cloud development environment and AI sandbox manager).
  * **Persistence:** Uses the remote sandbox's internal disk state as the persistence layer, tagging and reattaching to existing environments using Daytona labels (`workspace_id`).
  * **Best for:** Persistent, stateful remote development environments where agents write, test, and maintain full codebases over long sessions.
* **OpenSandbox (`OpenSandboxWorkspace`)**
  * **What it is:** Runs against OpenSandbox, AgentScope's open-source sandbox runtime designed for managing isolated agent execution environments.
  * **Persistence:** Persists inside the sandbox filesystem and reattaches across sessions using sandbox metadata.
  * **Best for:** Self-hosting a dedicated sandbox management service with cloud-like lifecycle APIs without relying on third-party commercial SaaS providers.

### Comparison Table

| Backend | Isolation Level | Where It Runs | Persistence Mechanism |
| :--- | :--- | :--- | :--- |
| **Local** (`LocalWorkspace`) | None | Host OS | Host `workdir` folder |
| **Bubblewrap** (`BubblewrapWorkspace`) | Process / Namespace | Linux Host | Mounted `host_workdir` or temp dir |
| **Docker** (`DockerWorkspace`) | Container | Local / Remote Docker Engine | Bind-mounted `workdir` or ephemeral |
| **Kubernetes** (`K8sWorkspace`) | Pod / Container | K8s Cluster | PersistentVolumeClaim (PVC) |
| **E2B** (`E2BWorkspace`) | MicroVM | E2B Cloud | Sandbox filesystem (via metadata) |
| **Daytona** (`DaytonaWorkspace`) | Container / VM | Daytona Cloud or Self-Hosted | Sandbox filesystem (via labels) |
| **OpenSandbox** (`OpenSandboxWorkspace`) | Sandbox Runtime | Self-Hosted / Custom Server | Sandbox filesystem (via metadata) |

## 2. Why MCP Servers Run in the Sandbox & How the MCP Gateway Works

In `LocalWorkspace`, MCP servers run directly on the host. However, in all six **sandboxed workspaces** (Bubblewrap, Docker, E2B, Daytona, K8s, OpenSandbox), **the MCP servers run *inside* the sandbox, while your Agent and Toolkit run on the *host*.**

### 2.1 Why Must MCP Servers Run Inside the Sandbox?
1. **Security & Containment:** MCP servers are active processes that execute tools (reading/writing files, running database queries, executing scripts, or interacting with local binaries). Running them inside the sandbox ensures a rogue or hallucinated tool call cannot modify host files, access the host network, or leak host environment variables.
2. **Shared Filesystem & State Locality:** If an agent uses its built-in `Bash` or `Write` tool to generate a file inside a Docker container or an E2B cloud VM at `/workspace`, any MCP server the agent uses (e.g., a Git or filesystem MCP server) needs to see that exact same `/workspace` directory. If the MCP server ran on the host, it would inspect the host's hard drive instead of the sandbox's filesystem.
3. **Dependency Isolation:** An MCP server may require specific system packages, Node/Python versions, or CLI tools baked into the container image that aren't installed on the host running the agent orchestrator.

### 2.2 How the MCP Gateway Bridges the Boundary
Most MCP servers communicate over **stdio** (standard input/output pipes between a parent and child process), which cannot directly cross container or cloud VM boundaries. AgentScope solves this with an in-sandbox **MCP Gateway**:

```text
+-------------------------------------------------------+       +-------------------------------------------------------+
| Host                                                  |       | Container / Cloud Sandbox                             |
|                                                       |       |                                                       |
|  +-------+     +---------+     +-------------------+  | HTTPS |  +---------------+        +------------------------+  |
|  | Agent | --> | Toolkit | --> | GatewayMCPClient  | ==========> |  MCP Gateway  | -----> | MCP Server 1 (stdio)   |  |
|  +-------+     +---------+     | (MCPClient proxy) |  | Token |  |   (FastAPI)   |        +------------------------+  |
|                                +-------------------+  |       |  +---------------+ -----> | MCP Server 2 (http)    |  |
|                                                       |       |                           +------------------------+  |
+-------------------------------------------------------+       +-------------------------------------------------------+



1. **Inside the Sandbox:** A lightweight FastAPI process (**MCP Gateway**) starts up, spawns/connects to the MCP servers inside the sandbox, and exposes a REST surface (`GET /health`, `GET/POST/DELETE /mcps`, `GET /mcps/{name}/tools`, `POST /mcps/{name}/tools/{tool}`, `PUT /mcps/{name}/runtime-headers`).
2. **On the Host:** Your agent's toolkit is given proxy adapters (`GatewayMCPClient` and `GatewayMCPTool`) that behave identically to local MCP clients.
3. **Zero Open External Ports:** Rather than publishing a network port on the container, the host executes a `curl` command *inside* the sandbox via `exec_shell` to talk to the gateway over the sandbox's internal loopback (`localhost`), secured with a per-workspace Bearer token (plus an instance nonce on `/health` for `BubblewrapWorkspace`).

## 3. Stdio MCP Servers: Installation, Mounting, and Session Loading

For `stdio` MCP servers, **the MCP server binary is not installed on your host and mounted into the sandbox.** Instead, only the configuration (`StdioMCPConfig`) is saved in the workspace directory, and the actual MCP server process is installed and executed directly inside the sandbox.

### 3.1 What Lives in the Workspace Directory?

When you register an MCP server (via `default_mcps` or `workspace.add_mcp(...)`), AgentScope writes its JSON declaration (command, args, env) into `/workspace/.mcp`:

```text
/workspace/
├── .agentscope    # Gateway venv and runtime files
├── .mcp           # MCP declarations (JSON configs) stored per agent / session
├── data/          # Offloaded multimodal payloads
├── skills/        # Agent skills (SKILL.md files)
└── sessions/      # Session context and tool results

```

* In `DockerWorkspace` and `BubblewrapWorkspace`, mounting `workdir` / `host_workdir` to `/workspace` mounts these **state and configuration files**, not host binaries.
* In cloud/cluster workspaces (`E2B`, `Daytona`, `K8s`, `OpenSandbox`), `/workspace/.mcp` lives directly on the remote sandbox disk or PVC.

### 3.2 How Large Node.js or Python Stdio MCP Packages Are Installed

The agent on the host never installs the MCP server's Node/Python packages; it only receives lightweight JSON tool schemas over HTTP from the MCP Gateway. Inside the sandbox, packages are provided via:

1. **Pre-baked into the Sandbox Image (Production Best Practice):** Large Node.js or Python MCP servers (like Playwright/Puppeteer or heavy SDKs) are pre-installed globally (`npm install -g ...` or `pip install ...`) in your Docker image, K8s image, or E2B/Daytona template.
2. **On-Demand Package Runners with Shared Cache (`npx` / `uvx`):** If launched dynamically via `npx` or `uvx`, the package manager downloads and caches the package inside the sandbox's filesystem (or in `host_cache_dir` for `BubblewrapWorkspace`). Multiple sessions in the same workspace share this cache, so packages are downloaded once per workspace rather than once per session.
3. **Custom Scripts in `/workspace`:** If you place a custom script in `/workspace/my_mcp.py`, the sandbox sees the script file, and the Python interpreter inside the sandbox executes it.

### 3.3 Per-Session Isolation (`agent_id + session_id`) & Startup Speed

* **Who Calls `list_mcps()`:** The LLM does *not* call `list_mcps()` during its thinking loop. Instead, `await workspace.list_mcps(agent_id, session_id)` is a framework-level Python method called during **agent assembly** (before prompting the LLM) to build the `Toolkit` and inject tool schemas into the system prompt.
* **How Per-Session Loading Works:** MCP declarations are isolated by `agent_id + session_id` so that in-memory state, cookies, and login sessions inside a stateful MCP never leak between conversations sharing a workspace. On the first `list_mcps()` call for a given `(agent_id, session_id)`, the MCP Gateway spawns a dedicated child OS process inside the sandbox and keeps its `stdin`/`stdout` pipes open for the duration of that session.

| Scenario | Startup Speed on `list_mcps()` | Why |
| --- | --- | --- |
| **Pre-installed in Image / Template** | **Instant (~50–200ms)** | Binary/modules are already on the sandbox disk; the Gateway just forks a child process. |
| **2nd+ Session in the Same Workspace** | **Fast (~100–300ms)** | A new child process is spawned for the new `session_id`, but `npm`/`uv` cache already exists on disk. |
| **Cold `npx` Download in Fresh Ephemeral Sandbox** | **Slow (3–15+ seconds)** | If an ephemeral container has no pre-installed packages and no persistent cache mount, `npx` must download packages over the network on first connect. |

## 4. HTTP MCP Servers: Registration, Location, and Routing

For an **HTTP-type MCP (`HttpMCPConfig`)**, **nothing is installed or spawned inside the sandbox at all**, because an HTTP MCP server is already a running web service.

### 4.1 Where Each Component Lives

* **The Server Itself:** Lives wherever its URL points—such as an external SaaS endpoint (e.g., `https://mcp.amap.com/mcp`) or an internal microservice on your network.
* **The Configuration:** Stored as a JSON declaration (`url`, `headers`, `is_stateful`) in `/workspace/.mcp`, scoped by `agent_id + session_id`.
* **The Live Client Connection:** The active `MCPClient` object that makes outbound HTTP requests to that URL lives inside the **MCP Gateway** process inside the sandbox.

### 4.2 Registration and Connection Flow

1. **Registration (`add_mcp` or `default_mcps`):** Saves the `HttpMCPConfig` to `/workspace/.mcp`. No network calls happen at this stage.
2. **Connection (`list_mcps` during Agent Assembly):** On the first `list_mcps(agent_id, session_id)` call, the host sends the `HttpMCPConfig` to the in-sandbox MCP Gateway (`POST /mcps`):
* **If `is_stateful=True`:** The MCP Gateway opens a persistent HTTP/SSE session (`connect()`) from inside the sandbox to the remote URL and fetches the tool list.
* **If `is_stateful=False`:** The MCP Gateway connects briefly to discover tool schemas, and thereafter creates a fresh, ephemeral HTTP request per tool call.


3. **Updating Headers at Runtime (`set_runtime_headers`):** Calling `await client.set_runtime_headers(...)` on the host proxy relays `PUT /mcps/{name}/runtime-headers` to the live client inside the MCP Gateway without reconnecting.

### 4.3 Why Route HTTP MCPs Through the Sandbox Gateway?

* **Unified Architecture:** The host's `Toolkit` treats every sandboxed MCP identically via `GatewayMCPClient`, regardless of whether the upstream server uses `stdio` or `http`.
* **Network & VPC Isolation:** If an HTTP MCP server runs inside an internal Kubernetes cluster (`K8sWorkspace`) or private Docker network (`DockerWorkspace`), the sandbox can reach that internal URL directly, and all outbound agent traffic remains governed by the sandbox's firewall and egress rules.
